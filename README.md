В качестве HTTP-клиента для всех сетевых вызовов используется библиотека aiohttp (использование httpx строго запрещено).

Передача событий о переводах организуется через паттерн  Outbox, что гарантирует защиту от потери данных и решает проблему двойной записи. Фоновый воркер вычитывает событие из таблицы Outbox и вызывает метод адаптера взаимодействия с клиентом сети (где вызов Toncenter POST /api/v3/message выступает одной из возможных конкретных реализаций). Перед передачей запроса в адаптер формируется BOC с таймштампом срока жизни valid_until, который подписывается сид-фразой внутреннего кошелька. Реализация адаптера инкапсулирует детали сторонних клиентов, полностью скрывает их внутренние исключения и выбрасывает собственную иерархию ошибок приложения.

При возникновении низкоуровневых сетевых ошибок (timeout, reset by peer, socket closed и т.д.) выполняется до 3 повторных попыток отправки. Если после 3 попыток сервер продолжает отвечать сетевой ошибкой или произошел сбой на этапе вещания, перевод остаётся в статусе pending с рассчитанным предельным временем ожидания (expires_at = valid_until + Grace Period). Это исключает риск ложного сбоя, при котором запрос фактически дошел до сети, но ответ был утерян. Если отправка прошла успешно, полученный msg_hash фиксируется в базе данных. `(для сетевых ошибок тоже нужно сохранять msg hash так как в дальнейшем по нему нужно будет искать транзакцию)`

Отслеживание завершения перевода построено на двухконтурной схеме:

Основной контур (SSE): Сервис подписывается на поток транзакций внутреннего кошелька с параметром min_finality: "finalized".
Резервный контур (Polling) и фиксация таймаутов: Для обработки возможных разрывов TCP-соединения каждые N минут запускается поллинг. Поллинг определяет время создания самой старой активной записи в статусе pending в пределах ее TTL и запрашивает у адаптера транзакции за временной интервал от этого минимального времени start_ut до текущего момента end_ut (в случае Toncenter — обращением к /v3/transactions). `(тут если не понятно могу на примере объяснить. и самое главное в ton. tx hash это не msg hash. это разные хэши. Там в транзакции много разных хэшей ext msg hash или msg hash это то которое было сгенерировано после создания boc в коде. остальные хэши генерируются на нодах или валидаторах)` Полученные транзакции фильтруются по полю msg_hash непосредственно на стороне адаптера.
Если время ожидания транзакции истекло, а подтверждение не пришло ни через SSE, ни через поллинг, перевод с полной уверенностью признается утерянным в сети TON, переводится в статус failed и инициирует отправку вебхука.

При определении финального статуса перевода (completed или failed) событие отправляется через брокер сообщений на идемпотентный обработчик, который обновляет данные в базе и публикует событие завершения. На это событие подписывается Webhook-воркер и отправляет подписчику подписанный HTTP-запрос. Если получатель вебхука недоступен, воркер совершает до 3 повторных попыток отправки, после чего фиксирует сообщение об ошибке в логах.

valid_until — параметр структуры сообщения в сети TON, указывающий точную метку времени (Unix timestamp), до которой транзакция сохраняет валидность. Если сообщение не успевает попасть в блокчейн до наступления этого времени, ноды сети его гарантированно отклоняют.
Grace Period — технологический временной зазор (обычно 2–5 минут), добавляемый поверх valid_until для компенсации рассинхронизации системных часов нод и задержек обновления данных на стороне API Toncenter.

## Как протестировать сервис

Тестируем перевод на Testnet:

- Создаем `.env` (пример `.env.example`)
- Заполняем:
    - `TONCENTER_API_KEY` - берем отсюда, @tonapibot, обязательно указать testnet при создании
    - `API_TOKEN` - Bearer-токен
    - `WEBHOOK_URL` - URL адрес вебкуха, куда отдавать сообщения о транзакциях
    - `TON_WALLET_MNEMONIC` - 24, не 12 слов
    - `TON_WALLET_ADDRESS` - Адрес кошелька в Testnet, должен называться на 0Q...
    - `TON_WALLET_VERSION` - стандарт смарт-контракта кошелька в TON (по умолчанию v5r1)
    - `TON_NETWORK_GLOBAL_ID` - для `v5r1` `-239` mainnet или `-3  testnet
    - `TONCENTER_SSE_URL` - URL адрес стриминг апи (по умолчанию - https://testnet.toncenter.com/api/streaming/v2/sse для testnet) 
- Остальные переменные окружения можно оставить тестовые или заполнить по желанию

## Полезная литература

BOC - Bag of cells. В блокчейне TON абсолютно всё - от баланса кошелька и кода смарт-контракта до транзакций и сообщений — хранится в виде древовидной структуры, состоящей из таких ячеек (Cells). BOC — это сериализованный (упакованный в байты или Hex/Base64 строку) массив этих ячеек, предназначенный для передачи по сети.
https://docs.ton.org/foundations/serialization/boc

The Open Network (TON) — это децентрализованная экосистема на блокчейне TON. TON стремится устранить распространенные ограничения блокчейн-сетей, такие как масштабируемость, скорость и удобство использования.

Outbox — это архитектурный шаблон для гарантированной и надежной отправки сообщений (событий) из базы данных в брокер сообщений (например, Kafka или RabbitMQ) без риска потери данных.
https://tproger.ru/articles/python-cqrs--piwem-raspredelennye-sistemy-bez-boli--sagas--outbox--event-driven-
https://habr.com/ru/articles/969512/


SSE (Server-Sent Events) - это технология, при которой клиент открывает один обычный HTTP-запрос, а сервер не закрывает соединение и по мере появления событий присылает их клиенту в виде текстового потока. Передача идёт только в одну сторону: от сервера к клиенту.
Отличия от вебсокета:
* сервер -> клиент (у вебсокета дуплекс <->)
* http протокол (у вебсокект свой протокол поверх tcp)
